# 四卡 Actor、Judge 并存压测

四个主要 GPU 作业都使用 gpu41 的同一组四张 NVIDIA A800-SXM4-80GB，设备 UUID 和运行时清单一致。Actor 和 Judge 的独立环境均为 Python 3.11.16、vLLM 0.19.1、torch 2.10.0+cu128、CUDA 12.8，驱动 580.65.06。分配规格为 4 卡、24 CPU 和 384 GiB 主机内存。

**C 证明了每张卡能同时部署一个 Qwen3.5-9B 实例和 gpt-oss-120b 的一份 TP4 分片，并运行生成与打标。没有布局满足联训验收的全部条件。**

## 启动、显存和运行故障

- A 按先启动 Judge、Judge level-1 休眠、再启动 Actor 与检索器的顺序运行。188904 的冷启动分别用时 258.46 和 360.62 秒，Judge 首次休眠 13.25 秒。首批 Actor 休眠 17.04 秒、Judge 唤醒 5.01 秒，换回时 Judge 休眠 2.42 秒、Actor 唤醒 9.16 秒。第二批 GPU1 和 GPU2 的 Actor EngineCore 在同一秒退出。已保留 2 个引擎的首条错误及后续请求错误。日志没有明确的 CUDA OOM 记录，宿主机根因证据不足。
- B 在 GPU0–1 运行 9B，GPU2–3 运行 Judge TP2。首次启动 Judge 116.22 秒、Actor 和检索器 97.15 秒。Judge rank 0 的权重为 34.38 GiB，KV 预算为 35.58 GiB。
- C 先启动 Judge TP4。首版 Judge 0.40、四个 Actor 均 0.45，检索器所在卡只剩 30.56 GiB，低于 Actor 启动要求的 35.66 GiB。唯一一次调整后，Judge 0.34，GPU1 Actor 0.37，其余 Actor 0.45。Judge 权重 17.22 GiB、KV 预算 9.35 GiB，均为 rank 0 日志值。四个 Actor 权重为 16.80 GiB，KV 预算依次为 16.61、10.27、16.61、16.61 GiB。调整后的首次启动 Judge 82.27 秒、Actor 与检索器 102.55 秒。
- C 三批分别记录到 63、58 和 51 次生成端 KV 抢占，GPU1 分别占 24、24 和 27 次。作为同题对照，早期 A 首批四个实例均为 0 次。C 的生成 KV 预算收缩，并与 Judge 共享 GPU 计算，原始回执显示生成端排队累积时间和请求抢占显著上升。两个因素单独贡献了多少没有隔离测量。

## 验收与边界

本轮实证支持 C 同卡并存及在既定负载下三批生成。A 未通过持续运行，C 第三批的交接经单独作业恢复，B 属于生成和打标验证。缺少真实参数更新的峰值与完整步骤耗时，无法按验收规则选出联训布局。更长的实际上下文、超过 16 的 Judge 并发、三批以上的持续压力、具有非零优势的更新及更新后的显存重复性均未覆盖。
