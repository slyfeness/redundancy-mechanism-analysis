# 生成、打标与参数更新的交接

## 批次身份

一次生成批次包含冻结训练清单的 16 题、每题 8 条轨迹。控制器在所有启用的生成实例上核对权重指纹。试跑用该指纹、已冻结的模型 revision 和基础模型路径生成 `policy_snapshot_id`。每条打标记录、原生批次和评分产物都携带同一个 ID。

`handoff.jsonl` 每条记录对应一条原生轨迹，沿用 `score-events` 的 `traj_id`、`task_id`、`outcome`、`termination_reason`、`recording_complete`、`response_mask`、`grounding` 和 `events`。事件使用原生策略 token 区间。记录另带 `policy_snapshot_id` 与 `labeler_versions`，可追溯 Judge 模型、M3 提示词和代码提交。

## 更新前检查

1. 等待核心标注文件覆盖所有原生轨迹。对账依据是实际生成的 ID 和原生批次顺序。未判结果、记录不完整或终止状态不合格必须显式留痕，原有的整组门控适用于这些排除。
2. 检查行级快照 ID、任务、独立结果和原生 `response_mask`。确认每个计价事件有唯一的原生动作区间，`known_at` 等于该事件的可判轮次。R2b 仍使用冻结的 DocID 判定和现有 `score-events` 定价。
3. 给原生批次文件计算 SHA-256。FSDP 在读取优势前再核对原生文件哈希、策略快照身份与原生坐标。试跑中的 FSDP 写入独立目录，其测试快照不参与正式发布。

## R1 诊断

核心标注和 M3 用独立的并发队列。R1 逐轨迹写到 `diagnostics/r1-sidecar.jsonl`，与同批的策略快照、轨迹哈希和证据快照绑定。更新入口只读取核心标注和原生批次，因此 R1 可晚一个批次到达。对照试跑仍会等该批 R1 到齐，以测量最后一条轨迹完成后的标注等待时间。停止 Judge 或使其休眠前须排空已开始的请求。

DocID 在整轮结束后并入并行工具结果。M3 请求只含调用前的推理尾部、当前搜索词及更早轮次已注入上下文的证据摘要。原判分服务返回 HTTP 402 后，余下压测跳过正式判分，有最终答复的正式结果仍为空。A/C 的第三批仅在独立更新目录写入 `test_outcome`，来源为 `local_strict_match_test_only`。测试分数在内存中映射到现有计价器接口，更新入口再次核验规则哈希和测试判分回执哈希。
